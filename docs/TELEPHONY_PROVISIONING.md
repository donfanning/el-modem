# El-Modem telephony provisioning

El-Modem's modem workers remain independent of PBX management. Provisioning is
an operator command run outside a call; it does not add work to SIP/RTP or DSP
processing.

## Current adapter

The first adapter targets an existing Asterisk installation using PJSIP. It
reads credentials from the selected modem instances' saved Hayes profiles and
generates one managed include, `pjsip_elmodem.conf`. Only modem instances
explicitly listed in the provisioning map are included. It does not edit the
dialplan, trunk configuration, or other endpoints.

The dashboard exposes this as **Telephony setup** in each modem's action menu.
It reuses the saved SIP account, lets the operator select the PBX target and
existing Asterisk context/transport, previews mapped modem/AoR identities,
applies only the managed include after confirmation, and can check the local
Asterisk registration contacts against the modem's own registration state.
SIP credentials are edited in the existing per-modem SIP settings screen and
remain in the modem profile.
In the TUI, **Check link** evaluates the current form values without saving the
telephony map; use **Save map** to persist them. **Apply to Asterisk** requires
confirmation before writing the managed PBX fragment. It saves the proposed
map before applying so the adapter can read it, then restores the prior map if
planning or PBX file application fails. If that restoration also fails, the UI
reports that both the map and PBX files need inspection before retrying.

Create a private map file, for example `telephony-map.json`:

```json
{
  "schema": 1,
  "pbx": {
    "type": "asterisk",
    "host": "pbx.example.lan",
    "port": 5060,
    "context": "from-internal",
    "transport": "udp-transport",
    "config_dir": "/etc/asterisk"
  },
  "bindings": [
    { "modem": "modem-1" },
    { "modem": "modem-2" }
  ]
}
```

Set and save each modem's SIP user and password in El-Modem first. The
provisioner uses those as the account credentials for the corresponding
Asterisk endpoint. The context and transport must already exist in Asterisk.
With an explicit config directory, preview/check scans static includes in
`pjsip.conf` and `extensions.conf`, and refuses to plan against a missing
transport or dialplan context. Configurations generated by `#exec` are not
interpreted and require static includes for this check.
The adapter also refuses an existing `pjsip_elmodem.conf` include unless it
is inside its marked block in the main `pjsip.conf`; it will not silently adopt
an include from an unrelated file.
Choose a context whose dialplan behavior you understand; this tool does not add
routes or authorize outbound calls.
Each selected modem's saved registrar must point to the same PBX host and port
in the map. This check helps prevent copying a provider account into the local
PBX by mistake.
The Asterisk file adapter accepts passwords up to 256 characters and rejects
config delimiters/control characters rather than attempting to escape them into
`pjsip.conf`; this is a serialization safety limit, not a SIP protocol limit.

For inbound REGISTER, Asterisk requires the AoR name to match the SIP user in
the registration's `To` header. Asterisk's username endpoint identifier also
matches the SIP `From` username to the endpoint name. The adapter therefore
uses the saved SIP username for both endpoint and AoR names, with an
instance-prefixed auth object. It checks statically included PJSIP files for
name conflicts and refuses dynamic `#exec` configuration because it cannot
safely inspect those generated objects. Use unique SIP usernames for the modem
accounts. See the [Asterisk PJSIP configuration relationships](https://docs.asterisk.org/Configuration/Channel-Drivers/SIP/Configuring-res_pjsip/PJSIP-Configuration-Sections-and-Relationships/)
for the endpoint and AoR naming rules.

Preview and inspect the proposed change:

```sh
el-modem provision plan \
  --config ~/.config/el-modem/config.json \
  --map ~/.config/el-modem/telephony-map.json \
  --asterisk-dir /etc/asterisk
```

Apply it to an existing Asterisk config directory:

```sh
sudo el-modem provision apply \
  --config /home/alice/.config/el-modem/config.json \
  --map /home/alice/.config/el-modem/telephony-map.json \
  --asterisk-dir /etc/asterisk
```

The command rechecks that the selected transport and dialplan context still
exist immediately before apply. It backs up files it changes with owner-only
permissions (`0600`), writes the generated include with private permissions
matching the Asterisk config ownership, and adds or updates only a marked
include block in `pjsip.conf`. It does not invoke `sudo`, reload Asterisk, or
change the dialplan. After reviewing the include, reload PJSIP through the
normal Asterisk administration path, then check registration and make a
controlled test call.

Check whether the files still match the selected modem profiles and map:

```sh
el-modem provision check \
  --config ~/.config/el-modem/config.json \
  --map ~/.config/el-modem/telephony-map.json \
  --asterisk-dir /etc/asterisk
```

`check` compares the generated file and include directive. Add `--live` when
running on the PBX host to query Asterisk's local CLI for each mapped endpoint
and AoR. It compares the loaded endpoint's authentication, AoR, transport, and
dialplan context with the desired configuration. It distinguishes a real AoR
contact row from Asterisk's always-present `Contact:` column heading and
reports a missing loaded AoR separately from an existing AoR with no registered
contact, along with the contact's qualify state (for example, `Avail` or
`Unavail`). This
checks configuration and registration visibility; it does not place a call or
verify media. With `--live`, the command exits successfully only if the managed
files, loaded endpoint fields, and at least one mapped AoR contact per modem
are present. A provisioned fragment contains SIP passwords; keep it, its
backups, and the map private. The command masks passwords in plans and never
prints the generated fragment.

Rollback the last managed file transaction without re-reading profiles or the
map:

```sh
sudo el-modem provision rollback --asterisk-dir /etc/asterisk
```

Rollback checks the recorded output hashes, ownership, permissions, backup
hashes (for schema-2 receipts), and transaction pointer before restoring
anything. Legacy schema-1 receipts predate backup hashes. If a managed file,
backup, or pointer has changed, it refuses to overwrite the later edit. If a
restore fails partway, it attempts to put files back into their pre-rollback
state and reports if that compensation also fails. After a successful
rollback, review the files and reload PJSIP through the normal Asterisk
administration path. Apply and rollback never reload Asterisk themselves.

## Boundaries and next steps

The modem profile is the source for its SIP account; the provisioning map is
the explicit opt-in and selects PBX context/transport. The generated
`elmodem_*` PJSIP namespace is owned by this tool. Changes elsewhere in
Asterisk are outside its scope. Applying a new map replaces only the generated
include and leaves old backups available for rollback.

The current implementation is an initial Asterisk file adapter. It does not
configure IAX peers, trunks, dialplan policy, firewall/NAT, or remote PBX APIs.
The provisioning layer turns saved profiles and explicit bindings into a
normalized `ProvisionRequest` containing a PBX target and modem SIP accounts.
Adapters implement the PBX-neutral `ProvisioningAdapter.plan(request)`,
`apply`, `check`, and `rollback` contract in `modem_provisioning.py`. They do
not receive DSP, worker, or supervisor objects; adapter artifacts and account
passwords are excluded from display representations. This keeps PBX-specific
configuration out of the call-processing path.
Qualification status (2026-10-26): five focused provisioning tests pass. An
isolated Asterisk 22.10.1 instance and an El-Modem instance on an internal-only
Docker network completed a real authenticated REGISTER. The modem's
`modem_dce.py` hash matched the current checkout. The adapter's live check
reported the endpoint as matching, the contact as `Avail`, and overall
consistent. Rollback restored the original `pjsip.conf` byte-for-byte and
removed the generated fragment. The fixture used a temporary credential and
was deleted; the shared lab PBX and external networks were not used. This run
also caught and fixed endpoint identification: Asterisk matches the endpoint
name to the REGISTER's From username, so the endpoint and AoR both use the
saved SIP username while the auth object remains instance-prefixed.
